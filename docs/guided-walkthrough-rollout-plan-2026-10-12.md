# Guided Walkthrough rollout: the missing problems

## Outcome and scope

Create an **in-playground Guided Walkthrough for every catalog problem that lacks one**. A guide is complete only when its steps can be applied in the real playground, its resulting design has passed review, and the published walkthrough is visible to a learner. This is not a project to add public `/problems/<slug>/` editorial pages, inflate assessment scores, or rewrite the assessor first.

Read-only AWS CLI checks on 12 October 2026 found 145 problem rows. Before this rollout published Ride Sharing, `diagrammatic_guided_walkthroughs` contained six records (five `1.0` records and one URL Shortener `1.1-review` record), despite the earlier working estimate of five published guides. Ride Sharing became the seventh record and Chat the eighth. After AI_008 passed its browser and strict assessment gates, it became the ninth public record; the refreshed live scan now shows nine walkthrough records and nine problem flags across all 145 problems. **136 problems remain without a walkthrough flag/record**. Recompute both tables before each batch boundary; a count alone is not an inventory. The 10 October public catalog export supplies an initial order, not a live source of truth.

Implementation is underway in local review drafts. Ride Sharing and Real-time Chat are the first two newly authored missing-problem guides to pass the browser and strict AI gates and be published; Chat's public GET response was verified with all 55 steps. The interrupted Chat browser-assessment submission is recorded separately and was not counted as an AI result.

## Existing product contract to reuse

- `app/models/walkthrough_models.py` defines `GuidedWalkthrough`: `problem_id`, `version`, `totalSteps`, `phases`, `steps`, and optional `requirementRevision`. Steps carry explanation and explicit `add_component`, `add_connection`, `update_component`, or accepted-decision actions.
- The API reads by `problem_id` from the walkthrough table at `GET /api/v1/problem/{problem_id}/walkthrough`; the dashboard also relies on the problem's `has_guided_walkthrough` flag. Publication must make both agree.
- The five tracked fixtures under `tests/fixtures/walkthroughs/` show the published format. The ignored `data/assessment-reference-candidates/walkthroughs/` directory contains revised local candidates for those same five; they are examples, **not** the source of truth for the missing-problem inventory.
- `scripts/walkthrough_fixtures.py` can replay explicit actions and detect duplicate nodes/edges, missing endpoints, and malformed steps. Browser apply/save/reload and actual AI assessment are separate checks.

## One-problem-at-a-time delivery loop

1. **Inventory and freeze the brief.** Join live problem IDs to live walkthrough keys. Recompute and exclude the IDs present in the current live inventory; do not infer a new problem from a static public guide or slug alias. Capture each selected problem's exact title, description, requirements, constraints, hints, and a content hash. Flag contradictory or ambiguous wording for a problem-specific decision; never silently rewrite it to make a design score well. Existing published `requirementSpec` is absent, so grade against the actual current brief unless an approved versioned spec is later published.
2. **Author a real guide.** Add one tracked JSON file under `data/guided-walkthroughs/<problem_id>.json` (a new source directory, separate from ignored test output). Follow the incumbent step/phase schema and teach that problem's architecture: assumptions, user and system flows, component choices, meaningful labeled connections, scaling and failure paths, security, observability, and tradeoffs as relevant. Every required capability must map to an explicit action or a clearly stated architectural reason. Reading an explanation must not count as an applied control. Use stable IDs and canvas positions, and keep all endpoints valid.
3. **Review the resulting design.** Validate the Pydantic model, unique sequential step numbers, matching phase ranges and total, supported action payloads, connected/intentional graph, and traceability from each brief requirement/constraint to steps and applied evidence. Check that the guide has not invented a stricter target or contradicted the catalog. Keep source and evidence in the repository so each guide is reviewable and reproducible.
4. **Test the learner journey.** In the real playground, apply the guide through its controls, inspect the final canvas, save, reload, and confirm nodes, edges, properties, accepted decisions, and applied-step IDs persist. Check a narrow viewport as well as desktop. Reuse the existing local FastAPI E2E harness and Playwright flow; do not inject a prebuilt graph and call that a UI pass.
5. **Check assessment trust.** Submit the graph the browser actually produced with the same problem brief the learner sees. Require five recorded live AI reviews for a release candidate: each scored at least **95**, `strong_alignment`, supported core requirements with valid evidence, and no critical or unsupported finding. This 95+ threshold and the browser gate were explicitly retained by the user. Also test an intentional missing-core-capability variant that receives a lower score/`needs_revision`, plus a reviewed valid alternative where the problem allows one. Record every run, including failures and unavailable reviews; do not cherry-pick, clamp, or use deterministic comparison as a substitute AI score. If a genuine guide defect appears, fix the content and rerun; if the assessor is inconsistent, track it separately rather than teaching to a misleading grade.
6. **Publish and verify.** After the content and result are reviewed, publish the versioned guide with a conditional create/update scoped to that problem ID and set `has_guided_walkthrough` consistently. Preserve a before-image and rollback path; do not overwrite an existing guide accidentally. Read back both tables, call the public GET endpoint, refresh the relevant frontend cache/session, and open the actual problem to verify the Guide tab and applied actions. Only then mark that problem complete and move to the next.

The browser E2E and publishing helpers should be made minimally reusable as each guide exposes a need. Tooling is support work, not the deliverable. The per-guide record is the deliverable.

## Order and checkpoints

The first five guide drafts above form the domain-spanning pilot. Video has passed its browser gate but failed its AI gate; its guide must not be published unless an actual guide defect is corrected and a new, fully recorded five-run gate passes. Run the same canonical gates for the other pilot candidates using their exact current briefs. Continue with live ID order after the pilot, reporting/reviewing in batches of 15. Recompute the missing set at every boundary; the list is keyed by problem ID, never by similar titles or static-page slugs.

Keep a tracked rollout manifest with each problem ID, title, frozen brief hash, guide path/version/hash, state (`missing`, `draft`, `structural-pass`, `browser-pass`, `assessment-pass`, `published`, `verified`), scores/verdicts, review notes, published timestamp, and rollback reference. This prevents an internal test pass from being reported as a visible published guide. Batch reports should state **newly authored / validated / published / visible** counts separately.

## Acceptance and stop rules

- The initial post-Chat count was 137 missing. After verified AI_008 publication, the latest live inventory scan is 145 problem rows, 9 walkthrough records, 9 true flags, and 136 missing; new or removed problems change the remaining count.
- No guide is published solely because it scores above 95. Valid requirement coverage, real applied evidence, UX replay, and content review must also pass.
- A provider outage is **unavailable**, not a 0 or a pass. A high numeric score paired with `needs_revision` fails.
- If a brief is contradictory, an action cannot be applied, or the saved graph differs from the assessed graph, pause **that problem**, record the issue, and continue with independent problems only after preserving the failure. Do not silently alter the problem, fake a score, or mark it complete.
- Do not touch the existing eight public walkthroughs, public guide/SEO pages, assessment scoring logic, or unrelated frontend behavior unless a specific new-guide failure demonstrates a necessary narrowly scoped fix.
